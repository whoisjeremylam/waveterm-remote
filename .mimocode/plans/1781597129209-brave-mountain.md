# Image Rendering Bug: IIP (iTerm2 Inline Image Protocol) Not Working

## Root Cause Analysis

### What We Know (Code Analysis Confirmed)

**The IIP handler IS registered on the correct parser.** The `sameParser: false` check in the investigation is misleading — it compares `terminal.parser` (a `ParserApi` wrapper) with `terminal._core._inputHandler._parser` (the actual `EscapeSequenceParser`). They are different object types, but `ParserApi` delegates to the same `EscapeSequenceParser` internally:

```
terminal.parser.registerOscHandler(1337, cb)
  → ParserApi.registerOscHandler()
    → CoreTerminal.registerOscHandler()
      → InputHandler.registerOscHandler()
        → EscapeSequenceParser.registerOscHandler(1337, new OscHandler(cb))
          → OscParser.registerHandler(1337, new OscHandler(cb))  ← SAME OscParser

terminal._core._inputHandler._parser.registerOscHandler(1337, iipHandler)
  → EscapeSequenceParser.registerOscHandler(1337, iipHandler)
    → OscParser.registerHandler(1337, iipHandler)  ← SAME OscParser
```

Both paths register on the **exact same `OscParser._handlers[1337]` array**. The handler should fire.

**The data flow IS correct.** `terminal.write()` → `CoreTerminal.write()` → `WriteBuffer._innerWrite()` → `InputHandler.parse()` → `EscapeSequenceParser.parse()` uses the same `EscapeSequenceParser` instance.

### Most Likely Root Cause: WASM `Base64Decoder` Failure

The `IIPHandler` uses WASM-based decoders (`Base64Decoder` from `xterm-wasm-parts`) for base64 decoding and image processing. These are bundled into `addon-image.mjs` via webpack. The critical data flow inside the handler:

```typescript
// IIPHandler.put() receives Uint32Array from parser
public put(data: Uint32Array, start: number, end: number): void {
    // HeaderParser parses IIP header (File=inline=1;size=...)
    const dataPos = this._hp.parse(data, start, end);
    // Passes Uint32Array.subarray() to WASM Base64Decoder
    this._dec.put(data.subarray(dataPos, end));  // ← Potential failure point
}

// IIPHandler.end() uses WASM for decoding
public end(success: boolean): boolean | Promise<boolean> {
    this._dec.end();  // ← WASM decode
    this._metrics = imageType(this._dec.data8);  // ← WASM image type detection
    createImageBitmap(blob, ...)  // ← Browser API
}
```

**Hypothesis:** The WASM `Base64Decoder` either:
1. Fails to initialize silently in the Electron environment
2. Receives `Uint32Array` data but internally expects/converts to `Uint8Array`, causing corruption
3. Returns an error code that causes `_aborted = true`, silently killing the handler

This would explain why:
- `storageUsage` stays 0 (no images added)
- No image layer created (no images to render)
- The handler appears to "never fire" (it fires but aborts silently in `put()`)

**Why Sixel works but IIP doesn't:** The Sixel handler (`SixelHandler`) uses the `sixel` npm package (pure JS decoder), NOT the WASM-based decoder. The IIP handler is the only one depending on the WASM `Base64Decoder` and `QoiDecoder`.

### Secondary Hypothesis: IIPHeaderParser Failure

The `HeaderParser.parse()` method (at `node_modules/@xterm/addon-image/src/IIPHeaderParser.ts:167`) returns `-1` for abort. If the header format from `chafa --format=iterm2` doesn't exactly match what the parser expects (e.g., missing `inline=1` parameter, wrong encoding), the parser would abort silently:

```typescript
public parse(data: Uint32Array, start: number, end: number): number {
    if (state === HeaderState.ABORT || state === HeaderState.END) return -1;
    ...
}
```

The `toSize()` decoder at line 74-80 throws on invalid size formats, which would trigger `_a()` (abort) via the `catch` in `_storeValue()`.

## Implementation Plan (If WASM is the issue)

### Option A: Replace WASM with JavaScript Fallback

Create a JavaScript-based `Base64Decoder` and `QoiDecoder` that can be used when WASM fails:

1. Create `frontend/app/view/term/base64-decoder.ts` — pure JS base64 decoder
2. Patch `ImageAddon.prototype.activate` to swap the WASM decoders with JS fallbacks after activation
3. Register the IIP handler manually on the public parser as a bridge

### Option B: Register IIP Handler on Public Parser (Simpler)

Since `terminal.parser.registerOscHandler()` works (confirmed by investigation fact #7), create a bridge that:

1. Intercepts IIP sequences before the parser
2. Decodes them with JavaScript
3. Creates images directly via `ImageRenderer.addImage()`

This avoids the WASM dependency entirely.

### Option C: Fix WASM Loading in Electron

Investigate why WASM modules fail to initialize in WaveTerm's Electron environment:
1. Check if `WebAssembly` is available in the renderer process
2. Verify the WASM binary is correctly bundled in the webpack output
3. Check Content Security Policy headers that might block WASM instantiation
